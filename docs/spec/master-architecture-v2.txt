Key relational rules

auth.users 1:0..1 profiles; user_roles joins users and roles.

contacts may be a guardian, parent or other lead; students are separate records; student_guardians is many-to-many.

class_groups 1:N class_sessions; students N:M class_groups via enrollments; sessions N:M students via attendance.

library_resources N:M access rules/entitlements; private resources require server-side entitlement checks.

leads belong to contacts and may later link to an enrolled student; retain source attribution and consent.

orders 1:N payments; payment gateway events are immutable and idempotently processed.

external provider IDs must be unique per provider/account and stored separately from internal UUIDs.

Secret-handling policy

Never put access tokens, payment secrets, WhatsApp tokens, service-role keys or OAuth client secrets in public source code, screenshots, shared documents or frontend environment variables. Use managed encrypted environment secrets; assign least privilege; rotate and revoke on staff changes; log secret access. This document specifies credential TYPES only and contains no real credentials.

09 | Integration and webhook architecture

Every external callback enters a dedicated HTTPS webhook endpoint. Verify signature/HMAC when supported; reject invalid payloads; persist provider event ID; enqueue asynchronous processing; deduplicate; retry with backoff; send exhausted failures to dead-letter review. Return successful acknowledgement promptly. Never trust browser-side payment status as proof of settlement.

Workflow | Input → processing → result

Website registration | Form → validation + consent → contact/lead → staff alert → enrollment review

Meta lead form | Lead webhook → authorized retrieval → dedupe → CRM lead → follow-up

WhatsApp | Inbound webhook → opt-in/context check → chatbot or human → reply via official API

SMS | Admin/trigger → approved template → provider → delivery callback → audit

Payment | Checkout initiation → hosted payment page → verified webhook → invoice/payment update → receipt/access

Social publish | Approved content → per-platform job → OAuth refresh → API publish → result/sync log

Live class | Scheduled class → meeting creation/link → entitlement check → attendance → recording link



10 | Payments architecture

Provider selection remains OPEN. Evaluate Sri Lanka merchant onboarding, supported cards and local payment methods, recurring billing, fees, refunds, settlement currency, webhooks, sandbox, reconciliation and data protection. Use hosted checkout to minimize card-data scope; do not store card numbers/CVV. Payment states: draft → pending → paid/failed/expired/refunded; grant paid entitlement only after verified server-side confirmation. Handle duplicate, delayed and out-of-order webhooks.

23 | Student registration, card issuing & attendance system

Submodule | Key operations | Required control

Admission | Create student, link guardians, grade, class and consent | Duplicate detection; guardian consent

Student card | Unique card ID, QR payload, print/reprint, issue/revoke/expire | Opaque signed/random token; never embed PII

Card scanning | Phone camera / USB scanner / dedicated reader | Authenticated scanner operator; device registration

Attendance | Validate enrollment and scheduled session; mark present/late | Idempotent scans; anti-replay/time window

Exceptions | Lost card, no card, offline, wrong class, duplicate scan | Manual override with reason + audit

Notifications | Optional arrival/attendance messages to guardians | Opt-in and delivery logs

Reporting | Session roster, absences, monthly summaries, export | Role and retention controls



Card format: print-ready academy branding, student name, student code, grade/class, validity and QR code. Avoid printing sensitive personal data. QR should resolve to a server-validated opaque card identifier, not a phone number, national ID or student profile URL. Card status: draft → issued → active → suspended/lost → revoked/expired. Reprints rotate the token and invalidate old cards.

Scanning workflow: operator selects class session (or device is bound to it), scans QR, server validates card + student + enrollment + time window, writes immutable scan event, upserts one attendance record per student/session, returns success/duplicate/error. Offline mode is optional; encrypted queued scans require conflict resolution and clock-skew handling. A QR card alone is not strong proof of physical presence; supervised scanning and anomaly monitoring are needed.

Suggested roles: Admissions Officer, Attendance Operator, Teacher, Academy Manager, Super Admin. Students and guardians may view only their own card and attendance history. Card issuance, overrides, exports and bulk imports require separate privileges.
