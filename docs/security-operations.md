# Access and operations runbook

## Access matrix

All application tables have RLS. The `academy` schema is not exposed to PostgREST. Only `academy_api` is exposed. Anonymous requests have no table or RPC access. There are no authenticated table-write grants or mutation policies. Invoker reads apply row **and** column restrictions. Fixed-search-path definer commands check DB-assigned permissions and scope again inside the transaction. Service-role/database-owner credentials bypass some of these safeguards and must **never** be used to serve client requests. No self-mutable role claims. Future migrations must explicitly enable RLS, restrict default function EXECUTE, and update the tests before exposure.

| Principal | Reads | Commands / hard limits |
|---|---|---|
| No role | Own minimal profile, approved member content; no family data without an explicit identity/link | No privileged commands |
| Student | Linked student roster fields, classes, card **metadata**, own attendance, entitled clean resources and own notifications | No card issue, scanning, contact lookup, overrides or role changes |
| Guardian | Explicitly verified account + individually verified child link; own contact, linked child's card/history/classes, entitled resources | Guardian role + verified link can append purpose-specific consent/withdrawal, no other guardian's contact |
| Teacher | Assigned groups/rosters, schedules, attendance reports/history (no birth dates/guardian phones) | Corrections with reason for assigned groups; supervised scan only with operator-bound device |
| Admissions officer | Roster + reviewed guardian contacts/classes | Admission and enrolment only, not card issue/export/override |
| Card issuer | Minimal roster/card data and print metadata | Issue, rotate/revoke; no corrections or raw hash lookup |
| Attendance operator | Schedule for active registered device; result of a supervised scan | Assigned device + operator + session group; cannot read whole student table or other devices' events |
| Marketing | CRM contacts/leads and editorial content | Draft CMS, record lead/follow-up; no student table, campaign spend or sending |
| Admin (academy manager) | Administrative scope, including audit | Requires JWT `aal2` **even with another role**. Academic/device provisioning, admissions, cards, scans with bound device, corrections, reports and content/CRM. No grant-management HTTP API. |
| Super admin | Administrative scope | Same MFA rule. Separate reserved `import.review` (and distinct `attendance.export` for admins); neither enables a bulk route in this phase. |

## First local run / commissioning

* **Credential-free checks**: Node 22.14+, non-root OS account and npm. `npm ci && npm run check` starts and deletes its own disposable PostgreSQL 17 cluster. The pinned npm fixture bundles native PG 17.11; `npm audit` does not cover native PostgreSQL fixes. Until a patched PG17 fixture package is available, restrict it to synthetic inputs on a private runner (owner-only socket on POSIX, authenticated loopback on Windows). Never use it for shared service, customer data or recovery. Use maintained PG 17.12 or later 17.x tools for the actual operator drill. The fixture never reads `DATABASE_URL`, links an account, or uses production records. See `tests/fixtures/supabase-contract.sql` for the small go-between used only by tests; it is **not** an Auth service or a migration.
* **Optional full local stack** (not exercised in this sandbox): install Docker and the official Supabase CLI. Check for existing local stacks/port collisions, then `supabase start` in a fresh, isolated checkout. `supabase migration list --local` should show the six migrations. Do not run reset on a shared database. Do not run the `tests/fixtures` DDL on Supabase. Supabase supplies `auth.users`, JWT helpers, managed roles and storage schema itself.
* Set `.env.local` from `.env.example` with the **loopback** Supabase URL for a local stack, its publishable/anon key and the allowed API origin. The only accepted remote Supabase URL is the confirmed Waruna Academy development tenant. A new tenant or custom domain requires a separate review. Use a runtime environment separate from the operator shell: leave management credentials and future integration fields empty. `npm run dev` runs the server only on request, default port 3000. Never paste CLI status output, keys, database URLs with passwords, recovery links or tokens into issues/chat. Keep production/staging secrets in separate managed stores.
* **Host deployment is not configured.** `api/v1/[...route].ts` and `vercel.json` are preparation only; Git deployment is disabled, CI performs no deploy/link/db push. For a newly **approved, isolated development** tenant: verify owner/ref/region and environment, migration history, database objects, existing auth users/triggers, any permissive Storage policies, endpoints and bucket-name collisions. Stop for review on any unexpected objects or a mixed-use project. Back up and demonstrate restore before applying reviewed migrations in order with the owner. Expose only `academy_api`, never `academy`; reload PostgREST schema cache if needed.
* Mirror `supabase/config.toml` explicitly in hosted Auth; local config does **not** change hosted settings. Use email confirmation and secure email/password changes, no anonymous/SMS signup, verified HTTPS redirects, rotating refresh tokens, 900-second access TTL and TOTP. Configure SMTP/recovery and verify SSO/OTP policies if required; never turn off verification to bootstrap. Apply shared ingress controls to API, Auth, Storage and direct REST endpoints, not just the Node handler.

### Owner-assisted role/identity setup (no automatic elevation)

1. After authorization, provision **synthetic** confirmed test accounts using the environment's normal Auth process and private test inbox. The trigger creates a profile with no roles; it does not inspect signup metadata. For pre-existing Auth users, stop and review individually; no automatic backfill of a live directory. Enroll and verify TOTP for the intended first administrator; confirm an AAL2 access token via the normal challenge.
2. Two-person review: verify account UUID, owner, target DB and intended role. A trusted migration/admin session, **not** a web request, binds an existing profile to a role. Example of the parameterized operation (bind actual values privately, verify exactly one returned row):

   ```sql
   insert into academy.user_roles(user_id, role_id)
   select p.id, r.id from academy.profiles p cross join academy.roles r
   where p.id = $1 and r.code = $2
   returning user_id, role_id;
   ```

   Record operator/ticket in the owner's restricted change log; DB role/link/device triggers log IDs only. A DB-owner session may have no `auth.uid()`; never fabricate an end-user actor. No role assignment by email, phone, request body or `raw_user_meta_data`. Review/remove old roles and verify access again after any staff change.
3. Provision a teacher, admissions officer, card issuer, scan operator and test family accounts separately. Through the admin endpoints, create a course, teacher group, session and operator-bound device. Build the session from **explicitly agreed** times, lateness and validity rules. Deactivate a compromised device immediately. Registrations can exist without portal accounts.
4. After verifying the guardian's identity, custodial relationship and consent evidence out-of-band, the owner binds `guardians.profile_id` and `verified_at`, and sets `student_guardians.access_verified_at` **only for that reviewed pair** in one audited transaction. Require the target profile not already linked to a different person; never overwrite an existing link to resolve a conflict. Record evidence reference privately. Bind `students.profile_id` independently after age-appropriate onboarding. Removing per-child verification ends future family reads. Do not infer family links from CRM data or shared phone numbers.
5. Test with two unrelated families, two teachers, AAL1/AAL2 admin, unverified guardian and a disabled device before admitting even pilot users. Revoke/rotate a test card and verify no new scan succeeds. Keep operator screens, printed cards and print queues supervised.

## Storage, secrets and retention

* Buckets `academy-library` (PDF) and `academy-imports` (CSV staging) are private, limited to 10 MiB. No authenticated upload/delete grants through policies. No public media bucket. An approved ingest/scan workflow must quarantine files, verify MIME/size/content and mark clean using separate least-privilege credentials. **No malware scanner or import uploader is running.** Do not substitute public URLs or privileged browser clients.
* Library policy requires the exact object of a cleared asset and a permitted library manager, current class rule or unrevoked time-bounded student entitlement. The API authorizes a resource server-side, records a **grant** (not proof of download), then asks Storage to sign using the same user JWT for 60 seconds. Recheck the actual Storage service in staging. Signed URLs already issued remain bearer grants until expiry. The API's TTL is not a global constraint on the provider's native signing endpoint: verify/directly restrict that route or adopt a server-only signer if a hard global TTL is required. No family can list import files.
* Do not log request bodies, QR tokens/digests, full auth headers, signed URLs, contact details, provider payloads or private conversations in proxies, Postgres parameter traces, CI or monitoring. Correlate with request IDs, action codes, counts/latency; restrict audit readers. Raw QR is returned once, never stored. A salted/unsalted hash of personal matching attributes is still sensitive: student duplicate fingerprints are never returned.
* Audit/consent/scan/adjustment/webhook/revision records are append-only to ordinary operations; this is **not** cryptographic tamper-proofing against the DB owner. Approve retention by data category (imports, minors' records, audit, backups, message bodies) with the data controller/counsel. Record and verify access/deletion/withdrawal requests. Limit processing promptly, revoke link/card/entitlement, and apply a reviewed pseudonymization/purge/backup-expiry plan; no blanket cascade deletes or indefinite default retention as policy. No claim of Sri Lanka PDPA compliance before legal review.

## Release, recovery and incident gates

1. Confirm repository visibility/IP and primary spec confidentiality before **any push**. Protect `main`, require PR review, migration/security review and CI checks. No credentials in CI; separate deploy role and protected dev/staging/prod environments. Never reuse the generic discovered project based on its name alone.
2. Local → isolated dev with synthetic data → isolated staging with sandbox accounts only → explicit client production approval. Verify actual Auth confirmation, refresh, MFA failure/downgrade/recovery, user JWT propagation through PostgREST, Storage private downloads/expiry, origin/CSRF and tenant isolation. Test both API **and direct platform endpoints** with least-privilege users.
3. Establish encrypted backups/PITR as available **after plan/cost approval**, agreed RPO/RTO and a restore drill to a separate isolated DB + Storage snapshot. Validate schema versions, counts, FK crosswalk, hashes, consent, RLS, and access after restore. Keep last known-good app release and migration history. Roll back by stopping writes, disabling workers, reverting the app and using a reviewed forward repair or verified restore; do not drop populated tables or silently clear audit history.
4. Before scale: trusted edge rate limits/WAF (per-instance memory limits are not fleet-wide), anti-spam on future public forms, device copy/replay anomaly review, least-privilege job roles, upload scanning, bounded queues and dead-letter operations. Define alerts for auth failures, scan anomalies, SQL latency/errors, webhook retries, reconciliation differences, storage/API spend. Provision monitoring only after privacy and ownership approval.
5. Incident: stop affected ingress/worker, disable device/revoke card or role/grant, rotate compromised server secrets, revoke sessions (short access TTL limits residual use), preserve minimal evidence, notify designated controller/security contacts per approved plan. Test recovery in isolation, reconcile, document approval before reopening. Review staff access, recovery codes, retention and budgets regularly.
